# The Week AI Started Doing the Job, Not Just Helping With It

There's been a pattern in how AI coding tools have been discussed for the past two years that I think broke this week. The framing has been autocomplete, meaning AI as a faster way to write code you already knew how to write. What's landing now is something different. These tools are being used, at scale, to close complete tasks without a human in the loop. That shift in how they're actually being deployed is more significant than any individual model update.

Here's what I found worth paying attention to.

## The autonomous coding agent story is no longer hypothetical

Reports from engineering leaders at mid-size product companies this week are describing a pattern that's becoming common, where you give an AI agent a GitHub issue, a testing suite, and repo access, and it returns a pull request that passes CI. It doesn't work every time, and not on anything architecturally novel, but it works reliably enough on scoped, well-specified tasks that it's changing how teams are sized and how work gets allocated.

What I find interesting is that this is happening because the workflow infrastructure around these models has matured, more than because of any single breakthrough model announcement. Tools like Cursor, Windsurf, and GitHub Copilot Workspace (Cursor and GitHub Copilot are both in my [AI dev tools directory](/ai-dev-tools)) have spent the past six to eight months building the context management, file system access, and iteration loop tooling that lets a model actually navigate a real codebase instead of just a toy prompt. The model capabilities are necessary but not sufficient. It's the scaffolding that turned capability into deployment.

The immediate implication for hiring is the one that's getting coverage, and I think it's real. Entry-level and junior engineering roles oriented around ticket closure, bug fixing, and straightforward feature work are going to compress. That's not a distant prediction anymore. Companies that are honest about their hiring plans are already describing this in terms of "fewer junior hires, same or higher output." What that means for the pipeline of engineers building toward senior roles is a more complex question that no one has answered convincingly yet.

## MCP is becoming the default integration layer

[Anthropic's Model Context Protocol](https://www.anthropic.com/news/model-context-protocol) has been around since late 2024 (I wrote about what it changes in [MCP Is Becoming the Default Integration Layer. Here Is What That Actually Means for How You Build.](/writing/mcp-integration-layer-what-it-means)), but something shifted this week in terms of adoption signals. Major cloud providers and developer tooling companies started shipping native MCP support, and the conversation in developer communities moved from "should we support MCP" to "which MCP servers are we building first." That's a different kind of momentum.

I think the significance here is commercial as much as it is technical. MCP is effectively standardizing how AI agents get context from external systems. If it becomes the dominant pattern, and the current adoption curve suggests it's heading that way, then the architectural question for every product that wants to be AI-accessible is "how does our data surface through MCP" rather than "how do we build an AI integration." That's a real simplification, and it has implications for how enterprise software gets bought and evaluated.

What I'd watch is whether the major CRM and ERP vendors move to support MCP natively. If Salesforce, ServiceNow, and SAP build MCP-native context APIs, then AI agents become dramatically more useful inside the enterprise workflows where most knowledge workers actually operate. That would accelerate the autonomous agent use cases significantly, and it would also shift negotiating leverage in enterprise software deals toward whoever controls the agent layer.

## Reasoning model economics are changing product decisions

OpenAI's o3 and Gemini 2.5 Pro have both seen meaningful price reductions in the past three weeks, and usage data from major API consumers is showing a shift. Tasks that were previously routed to cheaper, faster models are being re-routed to reasoning variants as the cost gap narrows. That's a story about what becomes economically viable when smarter models get cheaper, more than a story about model quality.

The product implication I keep coming back to is in decision support. There's a category of business problem where you really want a model that can reason carefully rather than just pattern-match, including diagnosis, contract analysis, financial modeling, and code review of complex logic. At the pricing from 18 months ago, those use cases were difficult to build around because the inference costs didn't support the required query volume. At current and near-future pricing, many of them become straightforwardly viable.

I'd argue this is the more important capability story than whatever the frontier benchmark is this week. The interesting question is whether o3 is cheap enough to run on every customer support ticket or every code commit to an internal repo, more than whether it can solve a competition math problem. That transition is happening faster than most enterprise technology plans anticipated.

## The security surface is expanding with the agent surface

Something that isn't getting enough coverage alongside all the agentic AI deployment news is what happens to the threat model when agents have persistent access to production systems. A single compromised agent context window, through prompt injection, a malicious dependency, or a manipulated tool response (which I got into later in [Prompt Injection Is a Product Problem](/writing/prompt-injection-is-a-product-problem)), can now be the entry point for actions across whatever systems that agent has access to. Red teams have already demonstrated it in controlled exercises.

The MCP expansion I mentioned above makes this more important to think about carefully, not less. Every new MCP server connection is a new trust boundary. Every tool an agent can call is a potential pivot point. The security industry is starting to talk about "agentic attack surfaces" as a category, and I think that framing is going to become standard quickly.

What I believe the practical response looks like is applying the same principles you'd apply to API access more generally, meaning least privilege, logging everything, and treating every external tool call as a potential adversarial input until proven otherwise, without waiting for a complete security framework. Teams deploying agents in production today that aren't doing this are accumulating risk faster than they're acknowledging.

## The question I keep coming back to

The story of this week, taken together, is that AI tools have crossed a threshold from assistance into execution on a meaningful class of tasks. That's not evenly distributed. It matters much more for software delivery than for most other knowledge work right now, but the pattern is directional.

What I think gets underweighted in most analysis of this is the compounding effect. If AI agents are already closing a meaningful share of engineering tickets, and the scaffolding and models keep improving at the pace they have, what does that share look like in 18 months? The answer matters a lot to anyone currently in or planning to enter technical roles, and it matters to any product organization whose competitive advantage depends on shipping speed. The interesting question is what the slope of the improvement curve implies about what you should be building toward, more than what AI can do today.
