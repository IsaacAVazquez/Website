# SEO and AEO audit, November 2, 2026

I ran this audit on November 2, 2026, against the live site at isaacvazquez.com and the code on main at fc1e32487. SEO here means how well regular search engines can crawl, understand, and rank the site. AEO, or answer engine optimization, means how easily ChatGPT, Perplexity, Claude, Gemini, and Google's AI answers can reach the pages, read them, and cite them.

The short version is that the technical base is in very good shape, and most of what is left sits outside the code, in three Cloudflare settings, in the publish dates on a large share of the articles, and in how loosely my profiles elsewhere connect back to the site. I found one real speed problem in the code, on the /writing index, where the lead image is both lazy-loaded and heavier than a phone needs. Findings 1 and 8 are fixed in the change that adds this report, and the decisions and dashboard work behind the rest are listed in `docs/TODO.md`.

## How I checked

I crawled all 312 URLs in the live sitemap plus the 67 internal link targets that are not in it, and for each page I recorded the status code, the canonical tag (the tag that names a page's preferred URL), the title, the description, the headings, image alt attributes, Open Graph tags, and the structured data, meaning the JSON-LD blocks that describe a page to machines. I read robots.txt, llms.txt, and the RSS feed, followed the redirects by hand, and requested pages with the user agents of the main search and AI crawlers. For speed I loaded six page types in headless Chromium on an emulated phone, twice each, adding 150 ms to every request, capping the connection at 1.6 Mbps, and slowing the CPU four times. That is lighter than Lighthouse's own throttling, so these load times run on the optimistic side. I also ran three searches through a web search tool to see what turns up for my name, and a separate pass rechecked every claim here against the raw crawl data before I finished.

## What is already right

All 312 sitemap URLs return 200. Every one has exactly one canonical tag pointing at itself, a title and a description that no other page shares, one h1, a lang attribute, complete Open Graph and Twitter tags, and JSON-LD that parses. Every image has an alt attribute, every sitemap page has at least one internal link pointing at it, no noindex page is in the sitemap, and the query-string variants I found, like the World Cup team views and the March Madness tabs, all point their canonical at the base page. Missing pages return a real 404, http and www both redirect to https://isaacvazquez.com, and the legacy /blog, /projects, and /work paths redirect permanently. The RSS feed carries all 249 posts, articles run from about 410 to 3,300 words with my byline, and each article's JSON-LD names me as the author and links my GitHub and LinkedIn.

Access for the answer engines' retrieval crawlers is set up the way the repo intends, apart from the robots.txt conflict in finding 2. OAI-SearchBot, ChatGPT-User, PerplexityBot, Claude-SearchBot, and Claude-User all got a 200, while GPTBot and ClaudeBot, which crawl for model training, got a 403 from Cloudflare and are disallowed in robots.txt. llms.txt lists every page in the sitemap outside /writing except /privacy.

On the five other page types I measured, the largest element on screen drew in 1.6 to 2.3 seconds, and layout shift ran from 0 to 0.004, where Google counts 0.1 or less as good.

### 1. The /writing index loads its lead image late and heavy

On the throttled phone runs, /writing drew its largest element at 5.0 and 5.3 seconds, which is past the 4-second line where Google calls this measure (largest contentful paint, or LCP) poor. That element is the first featured cover. Its img tag ships with `loading="lazy"`, so the browser holds the request until it has laid out the page, and its `sizes` value of `(max-width: 790px) 100vw, 50vw` has a phone with a high-density screen download the 1,200-pixel file, which is 158 KB as WebP against 39 KB for the 640-pixel version. That download also competes with everything else the page pulls in while it loads, including about 218 KB of background fetches that look like Next.js prefetching the article routes. In a rewritten copy of the page with lazy loading removed and a high fetch priority, served without the throttle, which flatters the result, the cover request started at 0.7 seconds and the cover still painted at 4.8 seconds. With the 640-pixel file as well, it painted at 2.2 seconds in both runs. So `priority={index === 0}` on the featured slot in `src/components/catalog97/Catalog97Writing.tsx` at line 246 is half of the fix, and the other half is a lighter file for that slot, through a lower quality setting or a `sizes` value that asks for less, which trades against how sharp the cover looks on a phone. When I measured the slot at every width for the fix, the same string turned out to send a 768px tablet the 1,920-pixel file for a 318px slot too, so the fix replaces it with the measured widths. These are lab numbers from my own throttling, and I couldn't get field data from real visitors, which the last section explains.

### 2. Cloudflare serves a second robots.txt in front of mine

Cloudflare prepends its own managed block, marked "BEGIN Cloudflare Managed content", to the robots.txt in the repo, so crawlers read both as one file. The managed block agrees with mine on the seven training crawlers my file blocks. It also disallows 24 agents my file leaves open, among them Bytespider, MistralAI-Training, Diffbot, GoogleOther, and Baiduspider and PetalBot, the search crawlers for Baidu and Huawei's Petal Search. And it says `Disallow: /` for Google-Extended, which `public/robots.txt` allows and `src/lib/__tests__/crawler-policy.test.ts` requires to stay allowed. The test passes because it reads the repo file and has no way to see what Cloudflare serves. Google merges every group that names the same crawler and settles a tie in favor of the less restrictive rule, so Google should still treat Google-Extended as allowed, which makes the real problem that the served file isn't the tested file.

Google-Extended also needs a decision of its own. [Google describes the token](https://developers.google.com/search/docs/crawling-indexing/google-common-crawlers) as covering both grounding, where Gemini pulls in search results while it answers, and the training of future Gemini models, and one token can't allow one without the other. So the allow in my file permits Gemini training too, which sits awkwardly beside the group in the same file that says model-training crawlers are not permitted. If citations in Gemini matter more to me than keeping the writing out of Gemini's training, the allow stays, and otherwise it should become a disallow.

Turning off Cloudflare's managed robots.txt would make the served file the tested file, but it would also drop those 24 extra disallows, so I'd first copy the ones I want into `public/robots.txt`, along with the Content-Signal line (`search=yes,ai-train=no,use=reference`). The 403s that GPTBot and ClaudeBot get come from Cloudflare at the edge, and [Cloudflare's docs](https://developers.cloudflare.com/bots/additional-configurations/managed-robots-txt/) describe the managed file as the layer that states preferences and AI Crawl Control as the layer that enforces them. I couldn't open the dashboard to see which setting produces the 403s, so I'd check that before turning the managed file off.

### 3. The site doesn't surface on my name in the one index I could check

In the web search tool I used, isaacvazquez.com didn't show up in the results for "Isaac Vazquez Berkeley Haas MBA" or for "Isaac Vazquez Civitech TextOut", even though a search limited to the domain found the RB vs WR article right away. So the site is indexed, and it isn't winning on my name. That is one search index on one day, and it isn't Google, so I'd treat it as a signal to watch. I have no backlink data, so the part I could check directly is how my own profiles connect back. My GitHub profile, IsaacAVazquez, has an empty website field and no bio, and its only link to the site goes to isaacavazquez.com, a misspelled alias that redirects, while the site's JSON-LD names that profile as one of the two `sameAs` links that tell machines the site and the profile belong to the same person. Setting the GitHub website field to https://isaacvazquez.com, pointing the profile link there as well, adding a one-line bio, and making sure LinkedIn's contact info and featured section link to the site would make that connection direct. I couldn't see the LinkedIn profile from here. A real Haas or Consortium profile page would be worth adding to `sameAs` once one exists and links back.

### 4. Many articles are dated before they went live

Five bulk commits added 108 articles, and every one of them carries a publish date earlier than the day it was added. The 36 Anthropic, Apple, and Microsoft essays merged in PR #518 on September 29, 2026, with dates going back to October 25, 2025. The other 72 came in on July 7 and July 20, 2026, as the Premier League, La Liga, and Formula 1 season series and a year of weekly Sunday articles, and the Premier League commit describes its series as backdated. Across the whole archive, 136 of the 249 articles first appear in git more than two weeks after their stated date, with gaps of up to a year, though git can't tell a backdated post from one that moved over from somewhere else, and the 15 added on August 9, 2025, may be that kind of move.

These dates go out as `datePublished` in the JSON-LD and on the page. Answer engines quote them, so a summary can end up saying I made an argument months before I wrote it, and if a piece draws on anything that happened after its stated date, it reads as foresight it didn't have. That is the same problem behind the four source links that the re-audit merged on September 27, 2026, pulled out, and three of those four articles are in the July 20 batch. The honest options are to date each batch to the day it went live, or to keep the dates and add a visible line saying when each piece was published, and either way I'd like to make that call on purpose.

### 5. Most articles cite nothing outside the site

80 of the 249 articles link to an outside source beyond the GitHub and LinkedIn links every article carries, and 49 of those link to three or more. Another 19 link only to the Wikimedia Commons credit under their cover photo, which credits the photo without citing anything, so 169 cite nothing. The company series is the best-sourced group on the site, with all 36 linking at least one source. The unsourced pieces that make the most factual claims are the 45 World Cup, La Liga, and Premier League recaps and a good share of the AI and market commentary, and an answer engine would want to check those claims before citing them, which a link to the primary source lets it do. Many of the rest are write-ups of my own projects, which are their own source. Any new link should be dated on or before the article's `publishedAt`, since a post-dated source was the problem the September re-audit found.

### 6. Cloudflare rewrites my email address

Cloudflare's email obfuscation turns every mailto link into a link to `/cdn-cgi/l/email-protection` and decodes it with JavaScript in the browser. 252 pages carry one of these links, which is the Email link on all 249 articles plus /contact, /resume, and /accessibility, and fetched without the script that path returns 404. On /contact, /resume, and /accessibility my address reads "[email protected]" in the visible text to anything that doesn't run scripts, and in three QA articles Cloudflare rewrites the example addresses inside code samples the same way, which breaks those samples for the same readers. The address is still readable in the JSON-LD on /contact, /about, and /resume and in llms.txt, since Cloudflare leaves script blocks and text files alone. For search this is mostly noise in crawl reports, but since I'm job hunting I'd turn Email Address Obfuscation off in Cloudflare, though keeping it is a reasonable choice if spam is the bigger worry.

### 7. Tool pages describe themselves as free apps with no ratings

43 tool and dashboard pages carry `SoftwareApplication` markup with a price of 0 and no rating or review. [Google's software app documentation](https://developers.google.com/search/docs/appearance/structured-data/software-app) requires either `aggregateRating` or `review` for that rich result, so these pages can't earn it. The markup still describes the pages accurately for other readers, so I'd leave it, and I wouldn't add ratings I wrote myself just to qualify.

### 8. A few schema values aren't in the vocabulary

On /score-pools/tracker and the noindex /score-pools/settings, the WebPage block's `isPartOf` reference has `"@type": "SportsApplication"`. That is one of the values Google lists for `applicationCategory`, and schema.org has no type by that name, so the WebPage still parses and Google just can't type that one nested node. The fix is `SoftwareApplication` at `src/app/score-pools/tracker/page.tsx` line 46 and `src/app/score-pools/settings/page.tsx` line 49. Six fantasy football routes, the draft tracker, the best ball draft tracker, the mock draft, the trade calculator, waivers, and weekly, set `applicationCategory` to "Sports", where Google's list has "SportsApplication", which is what the other sports pages already use.

### 9. Most articles share one modified date

210 of the 249 articles have `updatedAt` set to October 23, 2026, from the October voice review, and that date goes out as `dateModified` in the JSON-LD and as `lastmod` in the sitemap. The edits were real, and they went live on October 26 under the October 23 date, though when two hundred pages change on the same day the date tells a crawler less about which pages actually moved. From here on I'd bump `updatedAt` for changes to substance and leave it alone for wording passes.

### 10. http://www takes two redirects

http://www.isaacvazquez.com/about first redirects to https://www.isaacvazquez.com/about and then to https://isaacvazquez.com/about. One Cloudflare redirect rule from http://www straight to the https apex would make that a single hop. It only affects links written in that exact form, so it is cleanup.

## What I couldn't check

The Google Analytics connector still fails with "Account has been deleted", the PageSpeed Insights API was over its daily anonymous quota, and I couldn't open the Cloudflare dashboard, which would show how often each AI crawler actually reaches the site. The first things I'd open in Search Console are the page indexing report, to see how many of the 312 URLs are indexed, and the Core Web Vitals report for /writing, and I'd run one tool page through Google's Rich Results Test.

## The order I'd fix them in

I'd start with the code changes, the /writing cover and the two schema fixes, since all three are small and can be checked on a deploy preview. The three Cloudflare settings and the GitHub and LinkedIn links come next, since each one is a single setting, with the robots.txt change waiting on the Google-Extended decision and on copying the extra disallows over. The publish dates need a decision before any work happens. Sourcing the recaps and commentary is the largest piece of work, so I'd do it a few articles at a time, starting with the most-read ones once Search Console shows which those are.
